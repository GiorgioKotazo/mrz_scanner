Ниже — план в порядке приоритетности. Сначала устраняются риски неверного поведения и исчерпания памяти, затем оптимизируется стратегия сканирования, и только после этого выполняются косметические улучшения. Изменения в проект не вносятся.

## 1. Подготовить регрессионную базу и зафиксировать контракты

Этот этап необходим перед рефакторингом detection/postprocessing, чтобы оптимизация не ухудшила распознавание незаметно.

### Действия

1. Сформировать набор тестовых входов:
   - официальный образец DOCSAID;
   - синтетические или публичные TD1, TD2, TD3, MRV-A и MRV-B;
   - повороты 0/90/180/270;
   - изображения, требующие center crop;
   - изображения без MRZ: белое, чёрное, однотонное, обычная фотография;
   - очень маленькая и сильно вытянутая MRZ;
   - нечётные размеры изображений;
   - большие и панорамные изображения.

2. Не использовать личные паспортные фотографии как новые постоянные репозиторные fixtures. Для регрессионных тестов предпочтительны публичные, синтетические или обезличенные изображения.

3. Зафиксировать текущие результаты на четырёх уже проверенных изображениях:
   - распознанные строки;
   - формат и основные поля;
   - результаты контрольных цифр;
   - ориентиры polygon без требования побитового совпадения координат;
   - время и RSS как отправную точку, но не как жёсткие кроссплатформенные assertions.

4. Явно определить семантику результатов:
   - **нет приемлемой MRZ-области** → кандидат не создаётся, итоговый код `1`;
   - **правдоподобная область найдена, но OCR не разбирается или checksum failed** → кандидат возвращается, код `2`;
   - **все применимые checksum прошли** → код `0`;
   - ошибки командной строки не должны маскироваться под MRZ-кандидата.

### Критерий завершения

Есть воспроизводимый набор положительных и отрицательных сценариев, позволяющий обнаружить как потерю точности, так и ложные кандидаты.

## 2. Переработать detection/postprocessing: достоверность области и ограниченное потребление памяти

Эти работы лучше выполнять одной связанной задачей. Если сначала добавить проверки в старой системе координат, а затем полностью изменить масштабирование, часть проверок и тестов придётся переписывать повторно.

### 2.1. Устранить полноразмерный padded RGB и полноразмерный heatmap

Сейчас расход памяти определяется квадратом длинной стороны исходника. Следует перейти к ограниченному detection pipeline:

1. Создавать letterboxed detection input непосредственно в размере **256×256**, без промежуточного `RgbImage` размером `max(width, height)²`.
2. Сохранять метаданные преобразования:
   - масштаб по осям или общий масштаб;
   - смещения letterbox;
   - размеры исходного oriented-изображения.
3. Выполнять Otsu, поиск контуров и построение min-area rectangle:
   - предпочтительно в native resolution heatmap;
   - либо в другом строго ограниченном разрешении, если это необходимо для сохранения точности.
4. Преобразовывать найденный polygon обратно в координаты oriented-изображения математически, без создания полноразмерных heatmap/binary.
5. Сохранить прежние ML-контракты:
   - BGR;
   - NCHW;
   - нормализация `/255`;
   - размеры входов;
   - OpenCV-совместимая интерполяция.

При этом нельзя автоматически считать перенос бинаризации в 256×256 полностью эквивалентным текущему алгоритму: порядок resize → threshold и threshold → resize может менять контуры. Поэтому точность нужно сравнить на регрессионном наборе.

### 2.2. Исправить нечётные размеры в новой системе координат

Новый letterbox должен корректно обрабатывать нечётную разницу размеров: смещения на противоположных сторонах могут отличаться на один пиксель.

Если старая `pad_to_square` остаётся для других целей, отдельно исправить её контракт и добавить случаи 2×3 и 4×3. Если функция становится ненужной после рефакторинга — удалить её вместе с тестом старой реализации, а не поддерживать два пути padding.

### 2.3. Отсеивать ложные области до recognition

Добавить последовательные проверки:

1. Контур и rectangle не вырождены.
2. Обе стороны имеют достаточный размер в координатах detection.
3. Площадь области достаточна относительно detection-кадра.
4. Геометрия не противоречит MRZ после учёта допустимой перспективы.
5. Perspective transform применим, а warped image имеет ненулевые и технически осмысленные размеры.
6. Recognition запускается только после этих проверок.

Проверка уверенности sigmoid heatmap также желательна, но её порог нельзя назначать произвольно:

- сначала собрать статистику на положительных и отрицательных примерах;
- использовать широкие допуски для перспективы;
- не полагаться только на aspect ratio;
- не заменять все проверки требованием успешного `mrz::parse`, поскольку это устранило бы легитимный сценарий кода `2`.

Для немедленного устранения дефекта достаточно начать с объективно вырожденных областей вроде обнаруженной на белом изображении полосы 2×37. Более строгие confidence-пороги вводить только после калибровки.

### 2.4. Пересмотреть fallback-ранжирование неразобранного OCR

Длина OCR-строк не является надёжным показателем качества. Если остаётся несколько неразобранных кандидатов, лучше использовать:

- качество detection-области;
- отсутствие геометрических аномалий;
- структурные признаки OCR;
- детерминированный порядок попыток как tie-breaker.

Если дополнительные метрики пока не вводятся, лучше оставить первый правдоподобный кандидат, чем выбирать самый длинный мусорный OCR.

### Тесты и критерии приёмки

- Белое изображение 640×480 больше не создаёт MRZ-кандидата и завершается кодом `1`.
- Обычные изображения без MRZ не приводят к recognition inference на крошечных случайных контурах.
- Все четыре ранее успешных изображения продолжают распознаваться с теми же данными.
- Нет регрессии на маленьких и перспективно искажённых MRZ.
- Постобработка больше не создаёт буферы размером с padded full-resolution image.
- Для входа 6000×4000 отсутствует выделение heatmap/binary/contour workspace размером 6000×6000.
- Общий расход памяти по-прежнему включает само декодированное изображение и повороты, но больше не содержит дополнительного роста `max(width, height)²` из-за detection postprocessing.

## 3. Исправить стратегию попыток и ранжирование кандидатов

После стабилизации detection нужно упростить принятие решений в `run`.

### 3.1. Единая ранняя остановка для всех форматов

Рекомендуемое правило:

```text
checksum_consistent && !damaged_recovery → завершить попытки
```

Оно должно действовать одинаково для TD1, TD2, TD3, MRV-A и MRV-B.

Это устранит:

- до восьми лишних проходов после уже valid TD1/TD2/MRV;
- искусственный приоритет TD3;
- преждевременную остановку на восстановленном TD3, если дальше мог быть получен чистый результат.

### 3.2. Обработка `damaged_recovery`

1. Не завершать попытки на damaged-recovered кандидате.
2. Сохранять его как возможный best.
3. Любой clean checksum-valid результат должен быть предпочтительнее recovered.
4. Если после всех попыток существует только recovered checksum-valid результат:
   - сохранить текущий контракт кода `0`, поскольку все применимые checksum совпали;
   - обязательно сохранить вывод `Recovery`;
   - явно описать это поведение в README.

Это изменяет только момент остановки, но не вводит без необходимости новый breaking exit-code contract.

### 3.3. Сделать `score` форматно-нейтральным и прозрачным

Задать явный лексикографический порядок:

1. clean checksum-valid;
2. recovered checksum-valid;
3. parseable checksum-failed;
4. unparseable OCR.

Внутри checksum-failed учитывать долю успешных проверок относительно `applicable()`, а не только их абсолютное количество, чтобы TD3 автоматически не получал преимущество перед форматами с меньшим числом контрольных цифр.

Отдельный TD3-бонус убрать, если нет осознанного продуктового требования «паспорт всегда важнее остальных документов». Если такое требование существует, его нужно документировать, а не оставлять скрытым в арифметике score.

### Тесты

Проверить с помощью заранее сформированных результатов сканирования:

- clean valid TD1/TD2/MRV завершает цикл;
- recovered valid TD3 не завершает цикл;
- последующий clean результат заменяет recovered;
- valid кандидат всегда предпочтительнее invalid;
- доля checksum-проверок сравнивается корректно между форматами;
- равные результаты решаются детерминированно;
- ошибки отдельных попыток не затирают уже найденный кандидат;
- отсутствие приемлемых областей во всех попытках приводит к коду `1`.

## 4. Убрать лишние копии и вернуть polygon в координаты исходного изображения

Эти изменения связаны с представлением геометрии попытки, поэтому их удобно выполнять вместе.

### 4.1. Устранить лишние RGB-копии

1. Для full/0° передавать scanner непосредственно исходный буфер.
2. Не клонировать `image` при формировании `input`, если scanner только заимствует его.
3. Для ненулевых поворотов создавать только необходимый rotated buffer.
4. Для crop создавать один crop buffer без дополнительной копии при повороте 0°.

Не следует ради этого усложнять всю программу: достаточно локального заимствования или небольшого owned/borrowed представления попытки.

### 4.2. Хранить преобразование попытки

Для каждой попытки сохранять:

- rotation;
- crop offset;
- размеры промежуточного изображения;
- преобразование detection letterbox, необходимое scanner.

После получения polygon:

1. Координаты detection переводятся в oriented/cropped image.
2. Добавляется crop offset.
3. Выполняется обратный поворот.
4. В `ScanResult` или финальном `Candidate` сохраняется polygon в координатах исходного изображения.

В выводе явно указать, что координаты относятся к исходному файлу и выражены в пикселях.

### Тесты

- Четыре поворота одного изображения дают эквивалентный polygon после обратного преобразования.
- Crop с чётными и нечётными смещениями не теряет один пиксель.
- Координаты можно непосредственно использовать для наложения рамки на исходник.
- OCR-результаты после удаления копий не изменились.

## 5. Исправить CLI и вывод структурированных данных

### 5.1. Разделить usage errors и результат сканирования

Перейти с завершающего процесс `Args::parse()` на обрабатываемый вариант разбора аргументов, чтобы приложение само определяло код завершения.

Желательный контракт:

- `0` — checksum-valid MRZ, а также `--help`/`--version`;
- `2` — только получен правдоподобный, но неверифицированный MRZ-кандидат;
- `1` — ошибка аргументов, модели, декодирования изображения или отсутствие MRZ.

Покрыть тестами:

- отсутствие positional argument;
- неизвестный флаг;
- нечисловой `--threads`;
- `--threads 0`;
- `--help`;
- отсутствие модели;
- отсутствие MRZ;
- parse failure;
- checksum failure;
- checksum-valid результат.

### 5.2. Сделать вывод нейтральным к типу документа

Заменить терминологию:

- `Passport data` → `Document data`;
- `Passport number` → `Document number`;
- соответствующую подпись в check digits → `Document number`.

Дополнительно выводить:

- `optional_data_1`, когда присутствует;
- `optional_data_2`, когда присутствует;
- TD3 personal number сохранить под специализированным названием.

Пустые неприменимые поля лучше не печатать либо единообразно обозначать `N/A`.

### 5.3. Синхронизировать README

Обновить:

- коды завершения;
- раннюю остановку для всех форматов;
- поведение recovered-результатов;
- систему координат polygon;
- перечень выводимых optional fields;
- описание ограниченного detection preprocessing, если оно отражено в документации как техническая особенность.

## Финальная приёмка всего объёма работ

Работу можно считать завершённой только при выполнении следующих условий:

- Все быстрые тесты, форматирование и `clippy -D warnings` проходят.
- Четыре ранее проверенных MRZ-изображения распознаются без изменения данных.
- TD1/TD2/TD3/MRV-A/MRV-B проверены хотя бы на базовых integration fixtures.
- Белое и другие no-MRZ изображения не создают мусорных кандидатов.
- Нет recognition inference для явно вырожденных областей.
- Clean valid результат любого формата завершает лишние попытки.
- Recovered valid результат не препятствует поиску clean valid.
- Usage errors не имеют того же документированного смысла, что MRZ candidate.
- Polygon корректно накладывается на исходное изображение после rotation/crop.
- Detection больше не создаёт full-resolution padded/heatmap/contour-буферы.
- На больших и панорамных изображениях отсутствует прежний квадратичный рост дополнительной postprocessing-памяти.
- README, лицензионные метаданные и фактическое поведение согласованы.
